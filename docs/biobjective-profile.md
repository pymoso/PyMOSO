# Where the two-objective solvers spend a run

Phase 7, step 1 (docs/phase7-plan.md). Measured 2026-10-16 on
CPython 3.14.8, AMD Ryzen 5 5600X3D, serial. The tables are
`docs/biobjective-profile-tables.md`, generated by
`docs/bench_biobjective_profile.py report` from
`scratch/biobj/results/profile.jsonl` (raw runs; the log, with
`uptime` before and after, is `profile.log` beside it). Load average
was 0.28 at the start, and about 1.0 during the runs, which is the
benchmark's own single process.

Everything measured before this was RMINRLE on a cheap problem, and
mostly at six objectives. This is R-PERLE, R-MinRLE and R-SPLINE at
two objectives (R-SPLINE is single-objective: on the two-objective
problem it minimizes the first), budget 10,000, three seeds each, on
`ProbExpensiveBi` and `ProbExpensive`, with both MRG32k3a and
Philox-4x32.

## Method, and why the model can be trusted

The burn in `ProbExpensive*` never reads `x` or the stream, so a run's
trajectory is the same at every cost tier. Each configuration is
profiled once at burn 0, and its wall time at a tier is **modelled** as

    burn-0 wall time + feasible g() calls x burn per replication

**The model was tested, not assumed.** 36 real runs (six
configurations, Light/Moderate/Heavy, two repetitions each, MRG32k3a)
through `chnutils.solve()`, interleaved with burn-0 runs. Every one
returned burn 0's solution and end seed, and every **measured** wall
time was within 1.4% of the prediction (5 s to 147 s). The shares in
the tables for the tiers are therefore modelled from measured parts,
and the model's error is measured.

Burn per replication, **measured** on this machine: Light 0.44 ms,
Moderate 4.45 ms, Heavy 13.3 ms. That is about a third of the figures in
`probexpensive.py`'s docstrings.

Time and counts come from separate runs, because counting wrappers
distort timings. Every instrumented run returned the uninstrumented
run's solution and end seed, and every expected region reported
calls (the proof that each patch was reached). The counters were
seen detecting before they were trusted:
- the get_nondom counter reproduces T(n) exactly, and its bounded
  shadow n(n-1)/2, for n = 1-119, 200 and 500;
- the get_ncn early-exit shadow reached the same `ncn` as the real
  code on every one of its calls, in every run (asserted);
- the repeated-block counter read 0 from (30, 30), so it was checked
  from a boundary start, where it reads 1,003 `g()` calls, before the
  `BiEdge` configuration was added.

## What the numbers say

**1. At two objectives and any realistic cost, simulation is the run.**
On MRG32k3a it is 79-92% at Light, 97-99% at Moderate and over 99% at
Heavy. On Philox it is 97-98.5% at Light. Everything the framework
does besides the jump is 1.4-2.6% at Light and under 0.3% at Moderate.

**2. Dominance work does not matter at two objectives.** `get_ncn`,
`remove_nlwep` and `is_lwep` together are at most 0.07% of a
Light-tier run and 0.01% at Moderate; `get_nondom` is at most 0.01%.
The 94%-in-`get_ncn` figure is a many-objective result and does not
transfer. Note that these are the bi-objective algorithms'
`get_ncn`: in RMINRLE at M = 2 it was already 2.9% on a cheap
problem (the many-objective baseline), and with any simulation cost
it vanishes.

**3. The jump matters only for cheap simulations on the MRG family.**
On MRG32k3a the coordinate jump costs 1.3-1.7 ms per block (one block
per `hit()`). It is 5-19% of a Light-tier run, 0.6-2.4% at Moderate
and under 1% at Heavy. Modelled break-even: the jump is 10% of the run
when `g()` costs 0.2-1 ms per replication, and 1% at 2.5-11 ms. A
simulation of half a second, the README's own threshold for
parallelism, puts it near 0.02%. Philox already removes it (14-50 us
per block).

**4. The largest redundancy found is simulation, not comparison:
infeasible points simulated again in the same iteration.** Started on
the boundary that ProbTPA's efficient set touches (`BiEdge`,
x0 = (0, 20)), 14-22% of all `g()` calls are blocks that repeat a
point already simulated, and found infeasible, in the same iteration.
That is 2,000-3,500 calls per run. Most of it comes from `get_ncn`:
a deleted neighbour shared by several members of S is asked for once
per member, and again by part (b). `ne`, `pli` and `upsample` add the
rest. From the interior start it is 0-1%. In this fixture an
infeasible `g()` skips the burn, so the cost here is the jump, one
per repeated block. A problem whose `g()` learns infeasibility only
by simulating would pay the full replication cost.
This is `docs/rng-interface-design.md` §11 entry 13, deferred because
it is not result-preserving: the repeat draws further replications,
which can change a randomly-feasible point's outcome and moves the
high-water mark, and so the end seed. It is not a step-2 fix.

*Correction, the same day, after measuring it* (`docs/phase7-plan.md`,
step 1b). The end-seed part was reasoning, not measurement, and is
wrong as a general statement. A repeat moves the high-water mark only
when the repeated point has the largest point code touched in the
final iteration. A shadow cache left the solution, every iteration's
set and the end seed identical in all 42 runs tried, and in the full
suite. It is still not result-preserving by construction. A
randomly-feasible point's outcome can change; but the built-in solvers
fail on such problems anyway (step 1b).

**5. The end seed is recomputed every RA iteration.** `rasolve` calls
`Oracle.get_endseed()` once per iteration, a `stream_at` (~1.6 ms on
MRG), and only the last value is returned. It is 4-19% of a burn-0
MRG run, and at most 1.8% at Light.

**6. Inside `get_ncn`, part (b) does about three times the predicate
work an early exit would.** Done against needed for the same answer,
in the same order: 4,617 / 1,576 predicate calls (RPERLE), and
`calc_delta` 2,827 / 963, because each member's relaxation is
recomputed for every candidate. Immaterial at two objectives (point 2).
At many objectives `get_ncn` is the cost, so this is where it would
pay. The ratio there is not measured.

**7. `get_nondom`'s merge defect is confirmed in real runs and small:**
6-11% more `does_dominate` calls than the bounded loop, at the set
sizes these runs produce (mean |S| 2.3-2.6).

## Not measured here

- More than two dimensions, radius above 1, many objectives (see the
  many-objective baseline), `--crn`, `--simpar`, other Pythons.
- What the early exit in point 6 saves at M >= 3.
- Whether the end seed moves if infeasible points were remembered
  (point 4). By the reasoning above it should, which is why point 4 is
  reported, not fixed. (Since measured: it did not, in any run tried.
  See the correction under point 4.)
